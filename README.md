# rdgkit
Research Data Governance Toolkit - Space to find the answers to your research data governance questions.

## Local Development with Docker

Install Docker with Docker Compose (Docker Desktop on macOS/Windows, or Docker
Engine with the Compose plugin on Linux). On Windows, use a WSL2 workspace.
No host Ruby or Jekyll installation is needed.

From the repository root, launch the preview:

```sh
docker compose up
```

Open <http://localhost:4000>. Changes are picked up automatically with LiveReload
and polling. The first launch builds the image and installs dependencies; later
launches reuse cached layers and the named gem volume.

Stop the preview with:

```sh
docker compose down
```

The gem cache is retained. After changing the Gemfile, run
`docker compose up --build` to refresh the image; startup also installs any gems
missing from the persistent cache. The ignored local lockfile is used when
present and generated by Bundler when absent.

Compose overrides `baseurl` only for the local preview. Docker setup files are
excluded from generated site output; the GitHub Pages deployment workflow is
unchanged.

## Internationalization

The site uses `jekyll-polyglot`, with Spanish (`es`) as the default language
and English (`en`) available under `/en/` (beneath the deployment base URL).
Until English translations are added, English routes fall back to Spanish content.
Language builds run serially to avoid remote-theme temporary-file cleanup races.

Content currently lives in `pages/`. Name Markdown pages `page.es.md` or
`page.en.md`, and include a language and an explicit permalink in front matter:

```yaml
---
lang: es
permalink: /pages/example.html
---
```

An English counterpart must use `lang: en` and the **same permalink**. Preserve
existing `page_id` values across translations when present. Link to the shared
permalink using `relative_url`, not a language-specific source-file `link` tag:
Polyglot removes the non-selected translation from the active page set.
The HTML homepage also declares its
language and permalink; README and CONTRIBUTING are repository documentation,
not localized content pages.

Keep UI labels in [`_data/translations.yml`](./_data/translations.yml) under
matching `es` and `en` keys. In layouts and includes, use
`{{ site.data.translations[site.active_lang].nav_home }}` rather than hardcoded
labels. The existing GitHub Actions build runs Polyglot; no GitHub Pages
safe-mode plugin support is required.

[`_layouts/default.html`](./_layouts/default.html) preserves the theme's layout
while setting the HTML language from Polyglot's active language. Keep this
override in sync when upgrading the theme.

After dependency changes, run `docker compose up --build` for a local preview.

## Homepage styling

The homepage uses `layout: home` in `index.html`. The full-width hero is
rendered by `_layouts/default.html`; `_layouts/home.html` renders the card
grid without the theme's page title, table of contents, or metadata panels.
Each card expands with a click or Enter/Space to reveal the existing section
links, preserving access without adding clutter to the initial grid.

Brand colors are defined as `$color-primary-dark` (`#003B75`) and
`$color-primary-light` (`#1993b5`) in `_sass/_bootstrap_variables.scss`.
Theme component variables live in `_sass/_custom_variables.scss`, and the
`.rdg-hero-banner`, `.rdg-card-grid`, and `.rdg-card` rules are in
`_sass/_custom_classes.scss`. Navigation and footer styling reuse the theme's
HTML and require no additional include overrides.

## Interior page navigation and banner

The theme's `page` layout inherits the local `_layouts/default.html`, which
renders the full-width gradient banner before the content container. Interior
banners display `page.parent`, falling back to `page.title` and then `site.title`.
Section indexes use their own title; child pages declare the exact section
title as `parent`. The theme retains
the main content H1, table of contents, and page components unchanged.

The theme reads `site.data.sidebars[page.sidebar]`. Directory defaults in
`_config.yml` assign sidebars automatically for both `.es.md` and `.en.md`:

| Source directory | Sidebar data file |
| --- | --- |
| `pages/governancecycle/` | `_data/sidebars/data_governance_cycle.yml` |
| `pages/levels/` | `_data/sidebars/multilevel_data_governance_model.yml` |
| `pages/roles/` | `_data/sidebars/your_role.yml` |
| `pages/resources/` | `_data/sidebars/tools_resources.yml` |

For pages outside these directories, specify the layout and sidebar explicitly:

```yaml
---
layout: page
lang: es
title: "Definición global del proyecto"
parent: "Ciclo de Gobernanza de Datos"
nav_order: 1
permalink: /pages/governancecycle/0_definition.html
sidebar: data_governance_cycle
---
```

English translations use `lang: en`, the same `permalink` and `sidebar`, and
a `parent` matching the translated section title.
Do not prefix sidebar URLs with `/en/` or the deployment base URL; Polyglot
and the theme's `relative_url` handling apply those prefixes.

Each section has an `index.es.md` with an explicit directory permalink
(for example, `/pages/governancecycle/`), `has_children: true`, and a sidebar.
The index lists the same links as the sidebar. An English index must keep
the identical permalink and use `lang: en`.

Sidebar data uses `subitems` (nested `subitems` create a hierarchy).
This theme does **not** use Just-the-Docs navigation: `parent` is used by our
hero, while `has_children` and `nav_order` are descriptive metadata, not sidebar
generation or sorting controls. The order in the sidebar data is authoritative.
Its current labels are Spanish and are also used on English fallback pages.
No `_data/navigation.yml` is needed:

```yaml
subitems:
  - title: "Definición"
    url: /pages/governancecycle/0_definition.html
  - title: "Más fases"
    subitems:
      - title: "Recopilación de datos"
        url: /pages/governancecycle/1_data_collection.html
```

Interior content H1s are scoped to `.rdg-interior #main`, sized at `2rem`,
and have no negative top margin. A `1.5rem` margin below the hero separates
both sidebar and content from the banner without changing the theme grid.

The body uses a flex-column sticky-footer layout, with the outer content
container filling unused viewport space. Interior backgrounds remain white;
only the actual desktop sidebar grid column is grey, so it follows the theme's
responsive column widths rather than a fixed or percentage-based body gradient.
Its desktop pseudo-element extends that background through the left outer
gutter and up to the hero, stopping at the sidebar's actual right edge.
Desktop sidebar navigation has natural height and scrolls with the document.
These overrides leave Bootstrap's mobile sidebar collapse behavior intact.

`_includes/toc.html` overrides the theme 6.1.0 TOC include to translate both
the desktop heading and mobile toggle using `on_this_page` in
`_data/translations.yml`. It uses `site.active_lang` before `page.lang` so
English fallback routes display English UI even when their content is Spanish.
The generated JavaScript heading is serialized with `jsonify`. Keep this
override synchronized with the theme when upgrading.

Restart `docker compose` after changing `_config.yml`; Jekyll does not reload
configuration changes during watch mode.

## Image assets

- `assets/img/favicons/`: browser icons, the web app manifest, and its icons.
- `assets/img/icons/`: UI and topic graphics.
- `assets/img/logos/`: site, partner, and funder logos.

Set the navigation logo with `theme_variables.topnav.brand_logo` in
[`_config.yml`](./_config.yml), and footer images in
[`_data/footer.yml`](./_data/footer.yml). Use Jekyll's `relative_url` filter
for local asset URLs so they work with the site's `baseurl`.

[`_includes/head.html`](./_includes/head.html) overrides the hardcoded favicon
and Open Graph image paths in `elixir-toolkit-theme` 6.1.0. Keep it in sync
with the upstream include when upgrading the theme. Manifest icon paths are
relative to the manifest in `assets/img/favicons/`, so they also work when
the site is deployed under a subpath.
